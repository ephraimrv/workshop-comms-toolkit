1. From your data to R's data — the part nobody showed you

In Session 1 you were handed finished files: soil.otu.csv, kinetics, a .nwk tree. That is why R can feel like a tool that only works on data someone else has already prepared. The missing step is simple, and once you have it, R applies to your research directly.

Your spreadsheet is already almost a CSV

Your data almost certainly lives in Excel, Google Sheets, or Numbers — or in a table typed into Word. A .csv file (comma-separated values) is nothing more than that same table saved as plain text. You do not need special software to make one; the program you already use exports it:

If your data is inDo this
Microsoft ExcelFile → Save As → choose CSV (Comma delimited) (*.csv)
Google SheetsFile → Download → Comma-separated values (.csv)
Apple NumbersFile → Export To → CSV…
A table in WordFirst rebuild it in a spreadsheet (see below), then export. A Word table is not data R can read.

A CSV opened in a text editor is completely readable — it is just your table with commas between the cells:

sample_id,site,replicate,od600
S01,Anembo,1,0.42
S02,Anembo,2,0.51
S03,Badja,1,0.39
S04,Badja,2,0.47

R reads it in one line, and can immediately answer a question about it:

d <- read.csv("mydata.csv")
tapply(d$od600, d$site, mean)
Anembo  Badja
 0.465  0.430

That is your own data, your own question, answered by R. Nothing about it required a sequencing facility or a pre-made file.

Why CSV, and not the Excel file directly R can read .xlsx files with an extra package, but CSV is worth preferring: it is plain text, so it opens on any computer, survives email and old machines, never depends on which version of Excel you have, and you can see exactly what is in it. It is the format every data tool in the world agrees on.

The one idea that makes data "R-ready": tidy data

R works best when a table follows three rules. Together these are called tidy data:

  • One row per observation — one measurement, one row.
  • One column per variable — site, replicate, and reading each get their own column.
  • One value per cell — a number in a cell is a number, not 0.42 OD with the unit typed in beside it.

The reason some data does not "work in R" is that it was entered a different way. A common layout typed straight into Word looks like this:

            Anembo        Badja
  rep1      0.42 OD       0.39 OD
  rep2      0.51 OD       0.47 OD

This is readable to a person but hostile to R: there is no single site column, no replicate column, and 0.42 OD is text, not a number R can average. The very same measurements, entered tidily, are the four clean rows shown earlier — and those just worked.

Data-entry habits that quietly break R — fix them at the spreadsheet Every one of these is easier to avoid when typing than to repair afterwards:
  • Merged cells — R has no concept of a merged cell; it sees blanks.
  • Colour as meaning — a highlighted cell means nothing to R. If a value matters, put it in a column.
  • Units inside the cell — write 5, and add a separate units column or note. Not 5 mg.
  • Several ways of writing "missing" — pick one. Blank, NA, N/A and - are four different things to R.
  • Inconsistent capitalisation — this is the subtle one, see below.

Capitalisation is data too

R is case-sensitive, and so are sample names. In the soil dataset from Session 1, the sample list included Soil72, SOIL72, and SOIL82. To R those are three different samples. If two of them were meant to be the same sample typed inconsistently, that single slip silently splits one sample into two and quietly changes your results. Decide on one spelling convention for your labels and hold to it — this is won at the keyboard, before R ever runs.

2. Loading packages without typing library ten times

You already know from the Survival Guide that installing a package is done once per computer, and loading it with library() must be done once per session. When an analysis needs several packages, that becomes a stack of near-identical lines:

library(ape)
library(dplyr)
library(ggplot2)
library(readr)
library(phyloseq)

There is a shorter way. Put the names in a vector and load them all at once:

pkgs <- c("ape", "dplyr", "ggplot2", "readr", "phyloseq")
lapply(pkgs, library, character.only = TRUE)

lapply takes each name in pkgs and calls library on it. One line replaces five, and adding a package later means adding one word to the vector.

Two things about that line worth understanding

Why it prints a wall of names. After running it you will see several blocks like this:

[[1]]
[1] "dplyr"     "ape"       "stats"     "graphics"
[5] "grDevices" "utils"     "datasets"  "methods"
[9] "base"
[[2]]
...

That is not an error. Each time library() succeeds it quietly hands back the current list of loaded packages; normally you never see it, but lapply collects those answers and prints them. To silence it, wrap the call:

invisible(lapply(pkgs, library, character.only = TRUE))

Why character.only = TRUE is not optional. Normally you write library(dplyr) with no quotes — R accepts the bare word. But here the package name arrives as text inside a variable. Without that argument, R takes the variable's name literally instead of its value:

p <- "stats"
library(p)
Error: there is no package called 'p'

R looked for a package literally called p. Adding character.only = TRUE tells R "treat this as a string, look up its value" — and it works. This is the piece that breaks for people who copy the line and adapt it without knowing why the argument is there.

A plainer alternative, and when to prefer it A simple loop does the same job and is arguably clearer: 
for (p in pkgs) library(p, character.only = TRUE)
Its advantage: if one package fails to load, the loop makes it obvious which one, because it stops on that name. The lapply version is more compact; the loop is easier to debug. Either is a reasonable choice — knowing both, and why you picked one, is the point.

3. Three different ways to "clear" — and which one you actually want

"Clear," "reset," and "start fresh" get used interchangeably, but in RStudio they are three separate actions that clear three different things. Confusing them is why an analysis sometimes "still works" when it shouldn't, or "stops working" for no visible reason.

ActionHowWhat it clears · what survives
Clear the console display Ctrl + L Wipes the text on screen only. Every object and every loaded package is still there. Purely cosmetic.
Remove your objects rm(list = ls()) Deletes the variables you created. Loaded packages and the console text remain.
Restart R Ctrl + Shift + F10
(Session → Restart R)		 The real clean slate: objects gone, packages unloaded, session state reset. This is the only one that truly starts fresh.

On a Mac, use Cmd in place of Ctrl — Cmd + Shift + F10 to restart. Note that Ctrl + L looks like a reset but changes nothing except what you can see; and rm(list = ls()) empties your variables but leaves every package loaded. Only a restart does both.

The habit this unlocks: restart and re-run, often Restarting R, then running your script from the top, is the single best way to trust your own analysis. If it only works because of some object you made by hand an hour ago and forgot, a restart exposes it at once. A script that survives a fresh restart is a script you can defend to a thesis panel. Reproducibility is not an extra chore — it is what makes the result yours to stand behind.

Enter vs Ctrl+Enter — the same idea, two panes

This trips people because the same key does different things depending on where the cursor is:

  • In the Console (bottom pane), Enter runs the line immediately.
  • In the Source editor (a script, top pane), Enter just starts a new line. To run the current line and move on, press Ctrl+Enter (Cmd+Enter on Mac).

That is the whole of the "I pressed Enter in my script and nothing happened" mystery. The Survival Guide notes the fix in its decoder; the reason is simply that a script is a document you are editing, and Ctrl+Enter is how you say "now run this line."

4. Presenting your code in a thesis or poster: which font, and why

When you show code in a document — a methods section, a poster, a slide — the font matters, and it is a different font from the one your prose uses. Your university prescribes Times New Roman for the body of a thesis, and that is entirely correct for narrative text. Code is the exception, for a concrete reason.

Prose fonts vs code fonts

Times New Roman is a proportional font: a narrow i takes less width than a wide m. That is what makes prose comfortable to read. But in code, alignment carries meaning — indentation, columns of printed output, the + continuation prompt, an error message's ^ pointing at exactly one character. In a proportional font those stop lining up. Code needs a monospace (fixed-width) font, where every character occupies the same width:

Proportional (for prose)Monospace (for code)
Times New Roman, Calibri, Arial — comfortable to read in paragraphs, wrong for code because characters do not align. Consolas, Cascadia Mono, Source Code Pro — every character the same width, so indentation and output columns line up.
Safe, free monospace fonts you already have or can get
  • Consolas — ships with Windows and Microsoft Office, so it embeds into Word cleanly and needs no installing. The easiest default for most of you.
  • Cascadia Mono — free from Microsoft, ships with newer Windows.
  • Menlo or SF Mono — free, already on every Mac.
  • Source Code Pro, JetBrains Mono, IBM Plex Mono — free downloads if you want a specific look.
Set your code blocks to any of these; keep Times New Roman for the surrounding text. That combination is standard in every serious thesis that contains code.
Two cautions Do not reach for a "Nerd Font." Those are coding fonts padded with thousands of decorative icon symbols meant for programmers' terminals. The icons are useless in a document, and if you embed such a font and your examiner's computer does not have it, your code can appear as empty boxes (□□□). A plain monospace font is what you want.

Turn off "ligatures" for teaching material. Some fashionable code fonts (Fira Code, JetBrains Mono) redraw != as a single ≠ symbol. It looks elegant, but a reader trying to retype it will be confused about which keys to press. Fine in your own editor; avoid it in anything others must copy.

5. Small things worth knowing

None of these needs a section of its own, but each removes a small piece of mystery you will meet constantly:

You will seeWhat it is
c(1, 2, 3) c() means "combine into one vector." It is the most common function in R — it is how you make a list of values, such as the package names in Section 2.
x <- 5 The assignment arrow: "put 5 into x." = also works, but R users prefer <-. Type it fast with Alt+- (Option+- on Mac), which inserts the arrow with spaces around it.
'ape' vs "ape" Single and double quotes are identical in R. Use whichever you like; be consistent.
Tab Start typing an object or file name and press Tab — RStudio completes it. Fewer typos, and it shows you what is available.
Up arrow In the Console, the up arrow recalls your previous commands. You rarely need to retype anything.
str(d) · head(d) · summary(d) The "look at what I have" toolkit. str() shows the structure and each column's type; head() shows the first rows; summary() gives a quick distribution. Run these on any data before analysing it.
names(d) Lists the exact column names, with their exact capitalisation — the first check to run when R says it cannot find a column.
One habit that ties this together Before you analyse a dataset, run str() on it and read what R thinks each column is. Half of all "it won't work" problems are a column R read as text when you meant a number, or a name spelled differently from what you typed. Looking first costs ten seconds and saves the afternoon.
